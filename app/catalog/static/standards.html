What this demo is built on

Nothing here is custom: partners publish DCAT-AP with ODRL offers, the agreed minimum is a SHACL shape, terms link to shared vocabularies, and the catalogue can re-serve every record as CDIF.

1 · What a partner publishes

One JSON-LD file per partner. Organisation → datasets → distributions and access terms:

dcat:Catalog — one per partner, with dct:publisher (foaf:Agent)
dcat:Dataset — title, description, keywords, themes, spatial/temporal coverage, licence
dcat:Distribution — dcat:downloadURL (open) or dcat:accessURL (on request), media type
odrl:hasPolicy → odrl:Offer — assigner, permissions, prohibitions
odrl:permission / odrl:prohibition — action (use, distribute)
→ odrl:constraint (purpose, spatial) · odrl:duty (attribute, inform, obtainConsent, compensate)
schema:variableMeasured (optional) — variables with units and property IDs; needed for a rich CDIF description
dcat:Resource + schema:SoftwareSourceCode — software, listed under dcat:resource (DCAT 3): title, description, licence, schema:codeRepository, language, related publications and data, and its own ODRL offer

DCAT stops at the asset. It says what exists, who holds it and on what terms — not what is inside. The CDIF and CodeMeta views below are generated from the same entry; partners publish only catalog.jsonld. Rich, object-level description (e.g. an RO-Crate with files, provenance and workflows) stays with the data and can be linked from a distribution.

This is the same DCAT + ODRL offer pattern that Dataspace Protocol catalogues use, so connectors could replace static files later without changing the model.

The CDIF output follows the structure of the CDIF Data Description v1.1.1 example. It is a demo crosswalk, not validated against the CDIF shapes. DCAT stops at dataset level, so only datasets that describe their variables get a full CDIF data description — a concrete reason CDIF matters for cross-domain reuse.

3 · ODRL profile used for evaluation

ODRL defines the vocabulary but no standard evaluation algorithm, so the demo uses a deliberately small profile:

Actionsuse (covers all), distribute
Constraintspurpose, spatial with eq, neq, isAnyOf, isNoneOf
Dutiesattribute, inform, obtainConsent (→ request access), compensate
OutcomesAllowed · Allowed with duties · Request access · Depends on your request · Outside the offer · Not allowed

The catalogue states the terms; it does not enforce them. Enforcement is the job of connectors that negotiate on the same offer.

4 · Governance: the agreed minimum

Every harvested catalogue is checked against a SHACL shape. Agreeing this file is the metadata-governance conversation. Current rules: every dataset has a title, description, publisher, licence, at least one distribution, and an ODRL offer with an assigner; software has a title, description, publisher, licence, code repository and an ODRL offer. 5 · Vocabularies

Keywords, themes and ODRL purpose values link to concepts found through ontology lookup services. The links in this demo are examples only, to show the idea; they are not curated mappings. In the demo they live in config/vocab.json; in DigiLab they would come from the Vocabulary Hub PoC, which would also record whether a match is exact or only close. Unmapped terms are shown with a dashed ? link — the candidates for the Vocabulary Hub to resolve.

6 · Access methods

Harvested index: catalogues are fetched on a schedule or on registration, validated, and stored as Parquet (queried with DuckDB). Fast and resilient to a partner being offline, but only as fresh as the last harvest.
Live federated query: every partner catalogue is fetched at query time. Always current, but slower and incomplete when a partner is unavailable. Both modes run the same search and policy evaluation.

7 · Federation: what travels, what stays

Travels between partnersStays with the partner
Asset descriptions (DCAT-AP)The data and software themselves
Access terms (ODRL offers)Internal catalogues and repositories (Dataverse, CKAN, …)
Links to shared vocabulary conceptsRich domain metadata (RO-Crate, Darwin Core, CF, …)
Later: proofs of identity — signed catalogues, credentials for requestersThe decision to grant access

This follows the federated-catalogue pattern in Beyvers et al. (2026), Towards FAIR and federated data ecosystems for interdisciplinary research, PLoS Comput Biol 22(2): e1013806 — DCAT for discovery, ODRL for terms, each participant exposing only the minimal technical metadata needed. doi ↗
